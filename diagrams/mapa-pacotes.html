workflows REGISTRATIONS

The workflows: each file registers itself in init() on the core's DBOS context (core.Ctx()) with dbos.RegisterWorkflow. Adding one = adding a file; a subpackage (workflows/<name>/) only needs go generate ./workflows (the generated zz_generated.go carries the blank imports — main.go never changes). The embedded source (paths graph) picks everything up automatically.

FileResponsibilityFunctions
workflows.go Workflow hello-world (1 step: greet) + registration HelloWorld · init
pipeline.go Workflow pipeline (4 steps, no branch): fetch → parse → transform → store Pipeline · init
decide.go Workflow decide (step + if: left/right) Decide · init
steps.go Reusable steps (what the workflows execute) GreetStep · EchoStep
buy/buy.go Workflow buy (subpackage, 1 step: charge) — the template for workflows/<name>/ Buy · ChargeStep · init
zz_generated.go Generated (do not edit): a blank import per subpackage — written by cmd/workflowgen via go generate ./workflows —
steps_test.go Step unit tests (fake ctx) Test*Step
workflows_test.go The workflow runs: the env-driven TestMain boots the core once (the same lifecycle as production), and each test enqueues a workflow and asserts the executed steps TestHelloWorldRun · TestPipelineRun · TestDecideRunBranches · TestBuyRun
buy/buy_test.go The buy step unit test (fake ctx) TestChargeStepCharges

Not imported at runtime: it regenerates workflows/zz_generated.go (one blank import per workflow subpackage), so a new workflows/<name>/ is wired without editing main.go. Invoked by go generate ./workflows; the Dockerfile and CI run it too (CI fails on a stale file).
